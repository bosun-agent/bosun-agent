# 볼륨 복원 절차서 (관리자용, 11/7)

- 대상: BOSUN 백업 컨테이너 `bosun-backup`(offen/docker-volume-backup v2.50.1)이 만든 백업 파일
- 근거: offen 공식 문서 "Restore volumes from a backup", 11/6 실제 복원 연습(시원 님)
- 복원은 **관리자 작업**이다. AI Agent는 볼륨 안의 파일을 읽거나 바꿀 수 없게 막혀 있다.

---

## 0. 먼저 알아 둘 것

| 항목 | 내용 |
|---|---|
| 백업 저장소 | 볼륨 `bosun_backups` |
| 백업 파일 이름 | `backup-YYYY-MM-DDTHH-MM-SS.tar.gz` (한국 시간) |
| 백업 주기 | 매일 밤 11시 자동 + "지금 백업"(Agent에 말하거나 `docker exec bosun-backup backup`) |
| 보관 기간 | 7일. 지나면 자동 삭제 |
| 파일 안 구조 | `backup/<앱 이름>/…` (예: `backup/bosun-data-1102/hello.txt`, `backup/bosun-t16b-1102-redis/dump.rdb`) |
| 백업되는 볼륨 | bosun-backup에 읽기 전용으로 연결된 볼륨만. 지금: `bosun-data-1102_data`, redis 볼륨(`df3c0a74…`) |

명령은 한 줄씩 입력한다. 명령 뒤에 `#` 설명을 붙이지 않는다(맥 zsh는 `#`을 명령으로 읽는다).

---

## 1. 어떤 백업으로 되돌릴지 고르기

```bash
docker run --rm -v bosun_backups:/archive alpine ls -lh /archive
```
- 파일 이름의 시간이 한국 시간이다(왼쪽 날짜는 세계 표준시라 9시간 차이).
- 사고가 나기 **직전** 파일을 고른다.

고른 파일 안에 원하는 앱 데이터가 있는지 본다(아래 `<파일>`을 고른 이름으로 바꾼다).
```bash
docker run --rm -v bosun_backups:/archive alpine tar tzvf /archive/<파일>
```

---

## 2. 새 볼륨에 먼저 복원해서 확인하기 (원본은 건드리지 않음) — 권장

11/6 시원 님이 실제로 성공한 방식이다. 원본을 덮어쓰기 전에 "이 백업으로 정말 되살아나는지"를 먼저 본다.

① 확인용 빈 볼륨 만들기
```bash
docker volume create bosun-restore-test
```
② 백업 파일을 풀어 그 앱 데이터만 새 볼륨에 넣기(백업 저장소는 읽기 전용 `:ro`)
```bash
docker run --rm -v bosun_backups:/archive:ro -v bosun-restore-test:/data alpine sh -c 'tar xzf /archive/<파일> -C /tmp && cp -a /tmp/backup/<앱 폴더>/. /data/'
```
③ 내용 확인
```bash
docker run --rm -v bosun-restore-test:/data alpine ls -la /data
```
11/6 결과: `hello.txt` 내용 "hello-1102"로 원래와 같음 → 복원 가능 확인.

---

## 3. 원래 볼륨에 복원하기 (실제 사고 때)

**반드시 앱을 먼저 정지한다.** 켜진 채로 덮어쓰면 데이터가 꼬일 수 있다(공식 문서).

① 앱 정지 — Agent에게 "○○ 앱 꺼줘"(승인 1번) 또는 Portainer에서 스택 정지
② (안전) 지금 상태도 한 번 더 백업해 둔다
```bash
docker exec bosun-backup backup
```
③ 원래 볼륨에 복원 — 기존 파일 위에 백업 내용을 덮어쓴다
```bash
docker run --rm -v bosun_backups:/archive:ro -v <원래 볼륨 이름>:/data alpine sh -c 'tar xzf /archive/<파일> -C /tmp && cp -a /tmp/backup/<앱 폴더>/. /data/'
```
- 백업 이후에 새로 생긴 파일까지 없애고 **완전히 그 시점으로** 되돌려야 하면(DB 등), 공식 문서대로 볼륨을 비운 뒤 복원한다. 이 작업은 데이터를 지우므로 2번 확인을 끝낸 뒤에만 한다.
④ 앱 시작 — Agent에게 "○○ 앱 켜줘"(승인 1번)
⑤ 앱이 정상인지 확인 — 웹 화면 접속, Agent에게 "○○ 로그 보여줘"(승인)

11/8 결과(시원 님, 터미널): 시험 앱 `bosun-data-1102`의 원래 볼륨 `bosun-data-1102_data`에서 `hello.txt`를 일부러 "BROKEN"으로 바꾼 뒤, `backup-2026-11-08T13-50-25.tar.gz`에서 `backup/bosun-data-1102`만 풀어 덮어씀 → "hello-1102"로 되돌아옴, 앱 `bosun-data-1102-app-1` 정상 시작 → **원래 볼륨 복원 가능 확인**. (`tar: removing leading '/'` 메시지는 정상 안내)

## 4. 앱 종류별 주의

| 앱 | 주의 |
|---|---|
| 파일만 쓰는 앱(nginx 정적 파일 등) | 3번 ③ 덮어쓰기로 충분 |
| redis | `dump.rdb` 한 파일이 전체 데이터. 앱을 멈춘 상태에서 통째로 되돌린다 |
| mysql·postgres 등 DB | 앱 정지 → 볼륨을 비우고 복원(완전 되돌리기) → 시작. 쓰는 중에 찍힌 백업은 일부가 어긋날 수 있어, 중요한 DB는 백업 전에 앱을 정지하는 방식을 검토 |

---

## 5. 끝난 뒤 정리

확인용 볼륨은 지워도 된다(관리자 판단).
```bash
docker volume rm bosun-restore-test
```

## 6. 알려진 한계

- 백업 컨테이너에 **연결된 볼륨만** 백업된다. 새 앱의 볼륨은 연결해야 한다(지금은 관리자 작업, 11/6 결정 대기: Agent가 "볼륨 추가만" 하도록 할지).
- **이름 없는 볼륨**(예: redis의 `df3c0a74…`)은 스택을 다시 만들면 새 볼륨이 생겨 연결이 끊긴다. 오래 쓸 앱은 Compose에 이름 있는 볼륨을 쓴다.
- 예약 백업은 그 시간에 서버(맥북)가 깨어 있어야 실행된다. 놓친 시간은 다시 실행되지 않는다.
- 백업은 같은 서버 안(`bosun_backups` 볼륨)에만 있다. 서버 자체가 고장 나면 백업도 함께 잃는다. 실제 운영 전에는 외부 저장소(offen이 지원하는 S3·SSH 등) 복사를 검토한다.
